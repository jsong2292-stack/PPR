# 质量预警判定规则与实现说明

> 适用范围：PPR 质量智能分析助手的预警判定引擎
> 核心实现：`src/lib/quality-analysis/alert-engine.ts`
> 维护约定：**改规则必须同时改本文第 2 节和第 11 节**，接口/表结构变更需同步第 3、6、7 节；
> 企微推送相关变更需同步第 14 节。

---

## 1. 一句话概括

产品检验数据（`ppr_product_measurement`）保存后，系统按该记录的产品规格（`ppr_product_spec`，规格直接落在检验记录上，不再绕批次表）拿到每个指标的标准区间，对**每条记录的每个指标**判一次：

- 实测值**超出**标准区间 → 高风险事件（R3）
- 实测值**连续 3 个点进入接近带** → 中风险事件（R5）
- 其余 → 正常事件（R0）

判定结果写进预警事件表（`ppr_alert_event`），同时回写检验记录的质量标记（`quality_flag`）。整个过程自动发生，不需要人工点「扫描」。

产出的**中风险 / 高风险**事件还会推送到企业微信群机器人（见第 14 节），推送是判定之后的独立环节，不影响判定结果。

---

## 2. 规则定义

### 2.1 三条规则

| 规则码 | 规则名称 | 风险级别 | 触发条件 |
|---|---|---|---|
| `R3` | 超出标准区间 | 高风险 `high` | `实测值 < 下限` 或 `实测值 > 上限` |
| `R5` | 连续 3 点接近区间边界 | 中风险 `medium` | 同一批次、同一指标上，**连续 3 个及以上**的实测值都落在接近带内 |
| `R0` | 在标准区间内 | 正常 `normal` | 有实测值、区间可解析，且不满足 R3 / R5 |

三条规则**互斥**，同一条检验记录的同一个指标只会命中其中一条（优先级 `R3 > R5 > R0`）。

### 2.2 接近带（Proximity Band）怎么算

接近带是**贴在标准区间两端、向区间内部延伸**的两段窄带，宽度取标准区间宽度的固定比例：

```
接近带宽度 band = (上限 - 下限) × PROXIMITY_RATIO     // PROXIMITY_RATIO = 0.15
下限接近带 = [下限, 下限 + band]
上限接近带 = [上限 - band, 上限]
```

判定某点是否「接近」：先排除越限点，再看到最近那一侧边界的距离是否 `≤ band`。

```
distance = min(实测值 - 下限, 上限 - 实测值)
proximate = 未越限 && distance ≤ band
```

**算例**（本文档反复用到这套数，取自演示规格 `SPEC-25X4.2` / PPR S2.5 25×4.2 瓷芯管）：

| 指标 | 标准区间 | 区间宽度 | 接近带宽度 | 下限接近带 | 上限接近带 |
|---|---|---|---|---|---|
| 外径 | 25.000 – 25.500 mm | 0.500 | 0.075 | 25.000 – 25.075 | 25.425 – 25.500 |
| 壁厚 | 4.200 – 4.800 mm | 0.600 | 0.090 | 4.200 – 4.290 | 4.710 – 4.800 |
| 不圆度 | 0 – 0.350 mm | 0.350 | 0.0525 | 0 – 0.0525 | 0.2975 – 0.350 |

需求里给的例子「区间 2–10，实测 3 或 9 要告警」按同一公式成立：宽度 8，`band = 1.2`，接近带是 `2–3.2` 和 `8.8–10`，3 和 9 都落在带内。

> **注意**：单点进入接近带**不算**中风险，仍是 R0 正常，只是事件文本会写明「已进入接近带但未连续 3 点」。必须连续 3 点才升级。

## 3. 判定输入

### 3.1 取数

判定只读两张表，用一次 JOIN 取全（`alert-engine.ts` 第 306–319 行）：

```sql
SELECT m.id, m.record_no, m.batch_no, m.inspect_time, m.quality_flag,
       m.outer_diameter_mm, m.min_wall_thickness_mm, m.ovality_mm,
       s.outer_lower_mm, s.outer_upper_mm, s.wall_lower_mm, s.wall_upper_mm, s.ovality_upper_mm
FROM ppr_product_measurement m
JOIN ppr_product_spec s   ON s.id = m.spec_id
ORDER BY m.batch_no, m.inspect_time, m.id
```

- 检验记录按 `batch_no`（批次号）分组，**分组内部按 `inspect_time, id` 升序**——「连续」就是按这个顺序说的。
- 标准区间一律来自产品规格表：检验记录直接落 `spec_id`，不再绕批次表；`ppr_batch` 只是按批次号实时聚合的视图，不参与判定。
- `ppr_metric` 已退化为纯指标字典，不参与判定。
- `ORDER BY` 里的 `m.id` 是必要的兜底：同一时刻的多条记录需要确定的先后顺序，否则连续段判定会不稳定。

### 3.2 指标映射

引擎只判定下面三个指标（`METRICS`，第 57–61 行）：

| 指标编码 | 显示名 | 实测列 | 下限列 | 上限列 |
|---|---|---|---|---|
| `outer_diameter` | 外径 | `outer_diameter_mm` | `outer_lower_mm` | `outer_upper_mm` |
| `min_wall_thickness` | 壁厚 | `min_wall_thickness_mm` | `wall_lower_mm` | `wall_upper_mm` |
| `ovality` | 不圆度 | `ovality_mm` | **无（按 0 处理）** | `ovality_upper_mm` |

**不参与判定**的列：`max_wall_thickness_mm`、`max_outer_diameter_mm`、`min_outer_diameter_mm`。它们只是记录明细，规格表里也没有对应限值。不圆度只有上限，下限恒为 0。

### 3.3 不可判定的情况

以下情况该指标**不产生任何事件**，检验记录也不因它改变质量标记：

| 情况 | 说明 |
|---|---|
| 实测值为空 | `value === null`，例如该指标本批次没测 |
| 规格上限缺失 | 取不到上限就无法确定区间 |
| 区间非法 | `上限 ≤ 下限`，视为规格没配好 |

已存在的事件如果因为上述原因变得不再成立，会被**清理或关闭**（见第 8 节），不会留在队列里。

## 4. 判定算法

### 4.1 总体流程

```
evaluateAlerts({ batchNos? })
  │
  ├─ 1. 取数（可指定批次，不传则全量）
  ├─ 2. 按批次号分组
  ├─ 3. 对每个批次执行 planBatch()  ← 纯函数，无副作用
  │       └─ 对每个指标：
  │            a. 解析区间 → 算 band
  │            b. 逐点判定 judgeable / violation / proximate
  │            c. 扫描连续接近段，长度 ≥ 3 的整段标为中风险
  │            d. 逐点产出事件（越限 > 段末 > 正常）
  ├─ 4. 事务内写库
  │       a. 查已有引擎事件（含「是否被归档报告引用」）
  │       b. 按 (measurement_id, metric_code) 原地 UPDATE
  │       c. 不再成立的：可删的 DELETE，被引用的 UPDATE 成 closed
  │       d. 新增的批量 INSERT
  │       e. 按最高严重度回写 quality_flag
  ├─ 5. 返回汇总 { batches, records, created, high, medium, normal }
  └─ 6. 事务提交后：新增 / 升级的中高风险事件入企微推送队列（见第 14 节）
```

`planBatch()` 是纯函数（第 204–291 行），只依赖传入的行数据，不碰数据库——这是判定逻辑可以被单独验证的基础。

### 4.2 伪代码

```js
for (const metric of METRICS) {
  // ① 逐点标注
  const series = batchRows.map(row => {
    const range = resolveRange(row, metric);        // 上限必须有，否则 null
    const value = toNumber(row[metric.valueColumn]);
    const judgeable  = value !== null && range !== null;
    const violation  = judgeable && (value < range.lower || value > range.upper);
    const distance   = judgeable ? Math.min(value - range.lower, range.upper - value) : null;
    const proximate  = judgeable && !violation && distance <= range.band;
    return { row, value, range, judgeable, violation, proximate, runLength: 0 };
  });
  if (!series.some(p => p.judgeable)) continue;      // 整批该指标都没数据，跳过

  // ② 找连续接近段，只对长度 ≥ 3 的段落标中风险
  for (每个连续 proximate 段 [start, end]) {
    const length = end - start + 1;
    if (length >= PROXIMITY_RUN_LENGTH) {
      段内每个点.runLength = length;
      段内每个点.raise('medium');                    // 影响 quality_flag
      runEnds.set(end, start);                       // 只有段末产出 R5 事件
    }
  }

  // ③ 逐点产出事件，优先级 R3 > R5 > R0
  for (const [index, point] of series.entries()) {
    if (!point.judgeable) continue;                  // 不可判定 → 无事件
    if (point.violation)        emit(R3, 'high');    // 越限
    else if (runEnds.has(index)) emit(R5, 'medium'); // 段末
    else                        emit(R0, 'normal');  // 其余
  }
}
```

### 4.3 连续段的处理 ⚠️ 最容易误读的一处

一个连续接近段**只产出 1 条 R5 事件，挂在段末那个点**（`runEnds` 只记录 `end`）。但段内**所有点**的质量标记都会被抬到 `medium`。

以壁厚 4.200–4.800（接近带 4.200–4.290）、连续 3 点 `4.285 / 4.270 / 4.255` 为例：

| 点 | 壁厚 | 事件 | 事件级别 | `quality_flag` |
|---|---|---|---|---|
| 第 1 点 | 4.320 | R0 | normal | normal |
| 第 2 点 | 4.285 | R0（文本注明「已进入接近带但未连续 3 点」） | normal | **medium** |
| 第 3 点 | 4.270 | R0（同上） | normal | **medium** |
| 第 4 点 | 4.255 | **R5** | **medium** | **medium** |
| 第 5 点 | 4.360 | R0 | normal | normal |
| 第 6 点 | 4.400 | R0 | normal | normal |

即：**产品数据列表里会有 3 行显示「中风险」，但预警队列的异常页签里只有 1 条中风险事件。**

这样设计的原因是一个连续段在业务上是「同一个异常征兆」，展开成 3 条事件会让诊断和 8D 报告重复计数；而质量标记是逐条记录的属性，标出全部参与点便于在明细里回溯整段。**如果需要「队列里也看到 3 条」，改 `runEnds` 那段逻辑即可**（见第 11 节）。

### 4.4 一条记录多个指标同时异常

每条记录最多产出 3 条事件（外径 / 壁厚 / 不圆度各一条），质量标记取三者中最严重的：

```
quality_flag = max(R3=high, R5=medium, R0=normal)   // LEVEL_WEIGHT: high 2 > medium 1 > normal 0
```

例如同一条记录壁厚越限（high）、外径正常（normal），则事件有 2 条，`quality_flag = high`。

## 5. 事件编号（`event_no`）

```
event_no = QE-<检验日期 yyyymmdd>-<检验记录ID 补零到 3 位><指标后缀>
```

| 指标 | 后缀 |
|---|---|
| 外径 | `OD` |
| 壁厚 | `WT` |
| 不圆度 | `OV` |

例：`QE-20261112-003WT` = 2026-11-12 检验、记录 ID 3、壁厚指标。

**编号完全由数据决定**，不含随机数、不含时间戳。同一条记录重复判定必然得到同一个编号，因此批量插入不会撞 `uk_ppr_alert_event_no` 唯一键。

日期用 `getUTC*` 系列取值（第 157–161 行）：连接层时区为 `Z`，DATETIME 的墙上时间就是 UTC 字段，用 `getFullYear()` 会因服务器时区偏移算错一天。

## 6. 事件状态与质量标记

### 6.1 事件状态 `ppr_alert_event.status`

| 状态 | 落库时机 |
|---|---|
| `open`（待分析） | 新产出的 **high / medium** 事件 |
| `analyzing`（分析中） | 该事件已进入诊断流程；**重新扫描不会被打回 `open`** |
| `closed`（已关闭） | 新产出的 **normal** 事件（正常记录无需处理）；以及不再成立但被归档报告引用的事件 |

重算时状态的计算规则（第 372 行）：

```js
status = riskLevel === 'normal' ? 'closed'
       : (current.status === 'analyzing' ? 'analyzing' : 'open')
```

### 6.2 质量标记 `ppr_product_measurement.quality_flag`

由引擎按判定结果回写为 `normal` / `medium` / `high`。

**`error` 是数据来源层面的标记，引擎永不覆盖**——回写 SQL 带 `WHERE quality_flag <> 'error'`（第 444 行）。这样上游标记的「数据有问题」不会被判定结果冲掉。

### 6.3 事件来源 `ppr_alert_event.source`

| 取值 | 含义 |
|---|---|
| `engine` | 判定引擎生成，会被重算覆盖 |
| `legacy` | 历史演示或人工遗留数据，引擎**不碰**，队列和统计也**不显示** |

引擎只接管 `source='engine'` 且指标在 `ENGINE_METRIC_CODES` 内的事件（第 351 行）。人工录入的其它规则（如 R4）不会被重算误删。队列查询统一带 `WHERE a.source='engine'`，所以 `legacy` 事件不会污染演示视图。

### 6.4 推送状态 `ppr_alert_event.notified_level` / `notified_at`

| 列 | 含义 |
|---|---|
| `notified_level` | 已推送到企业微信的**最高**风险级别（`medium` / `high`），`NULL` = 从未推送 |
| `notified_at` | 最近一次推送成功的时间 |

只在推送**成功**后回写；事件回到正常（`normal`）或因为不可判定被关闭时会清空，让同一记录以后再异常时能重新告警。判定引擎靠它区分「新出现的异常」和「重算时一直存在的异常」，详见第 14 节。

## 7. 触发时机

判定**不需要人工操作**，以下动作保存成功后自动重算，并把结果一并放进 HTTP 响应（字段名 `alerts`）：

| 动作 | 接口 | 重算范围 |
|---|---|---|
| 产品数据 Excel 导入 | `POST /api/quality/master/measurements`（逐行） | 该行所属批次 |
| 新增产品数据 | `POST` 同上 | 该行所属批次 |
| 编辑产品数据 | `PUT /api/quality/master/measurements/[id]` | 新旧两个批次（改批次号时两边都要重算） |
| 删除产品数据 | `DELETE` 同上 | 删除前记录的所属批次 |
| 修改产品规格限值 | `PUT /api/quality/master/specs/[id]` | 该规格下的**全部**批次 |
| 手工全量扫描 | `POST /api/quality/alerts/evaluate` | 全部批次 |

规格改动会波及所有引用它的批次，所以走 `specId` 分支先查 `SELECT DISTINCT batch_no FROM ppr_product_measurement WHERE spec_id=?` 再逐个批次号重算（`refreshAlertsQuietly`，第 486–497 行）。

**判定失败不会中断数据写入**：`refreshAlertsQuietly()` 捕获异常后只 `console.error` 并返回 `null`，保存接口照常返回成功。这是有意的取舍——预警算不出来不该让业务数据存不进去。代价是失败时前端不会报错，需要看服务端日志。

前端的 `DataManager` 会把响应里的 `alerts` 汇总成一次提示：

```
导入完成：成功 6 / 6 条
自动预警：高风险 3 条，中风险 1 条
```

## 8. 幂等、外键与归档保护

这是实现里最需要小心的部分，因为**重复导入同一批数据必须得到完全相同的库状态**。

### 8.1 为什么不能「先删后建」

事件表是整条追溯链的起点，链路上有 `ON DELETE RESTRICT`：

```
ppr_alert_event ──CASCADE──▶ ppr_analysis_run ──CASCADE──▶ ppr_eight_d_report ──RESTRICT──▶ ppr_history_archive
```

一旦事件已生成 8D 报告并被历史归档引用，删除事件会直接报外键错误。所以重算的策略是：

1. **原地 UPDATE**：按 `(measurement_id, metric_code)` 找到已有引擎事件，更新其内容，**保持 `id` 不变**——`id` 是诊断/8D/归档的外键，必须稳定。
2. **不再成立的**：
   - 未被归档引用 → `DELETE`
   - 已被归档引用 → `UPDATE status='closed'`，并写明关闭原因，保住追溯链

判断「是否被归档引用」用的是查询里的相关子查询 `archived`（第 345–351 行）。这也是 `source` 列存在的原因之一：只处理引擎自己的事件，避免误伤。

### 8.2 幂等性结论

| 操作 | 结果 |
|---|---|
| 同一批数据重复导入 | 事件内容、级别、编号完全一致，不新增重复行 |
| 同一批数据重复导入（企微推送） | 事件级别不变时不重复推送，只有新增或升级才推送（第 14.2 节） |
| 值改越限后再改回正常 | 高风险事件被删除（或关闭），质量标记回到 `normal` |
| 值改成 NULL | 该指标事件被清理，其它指标不受影响 |
| 删除检验记录 | 事件随 `ON DELETE CASCADE` 一起消失，无残留 |

### 8.3 批次数据清理：按来源分开，谁的数据清谁

检验记录与采集数据之间**没有批次表**，批次号只是两张子表之间的字符串关联键，`ppr_batch` 是按 `batch_no`
实时聚合的视图，没有可删的行。产品数据与设备数据之间也没有从属关系，所以清理**不能跨来源级联**：

| 入口 | 清理范围 | 连带 | 实现在 |
|---|---|---|---|
| 批次总览页 / 产品台账下钻的批次列表 | 该批次的**检验记录**（产品侧） | 由这些记录产生的预警事件（事件挂在 `measurement_id` 上，不删就成孤儿，会继续级联到诊断任务/结论与 8D 报告） | `src/lib/quality-batch-cleanup.ts` + `DELETE /api/quality/master/batches?id=<批次号>` |
| 设备台账下钻的批次列表 | **本设备**在该批次下的**采集数据** | 无 | 同文件 + `DELETE /api/quality/equipment/{设备ID}/batches/{批次号}/readings` |

两边都清空后，这个批次号下没有数据了，视图里自然就没有它——**「批次消失」是清理的结果，不是清理的对象**。
所以「在本设备页删一行却把产品数据和别的设备的数据一起删掉」这类跨来源误删不会再发生。

处理规则：

| 情况 | 行为 |
|---|---|
| 该批次下没有检验记录（产品侧） / 该设备在该批次下没有采集数据 | 返回 `404`（「没有可清理的数据」） |
| 有数据、未带 `confirm=1` | 返回 `409` + `code=BATCH_HAS_MEASUREMENTS`（产品侧）或 `code=READINGS_HAS_ROWS`（设备侧）+ 真实条数与说明，此时**一个字节都不删** |
| 有数据、带 `confirm=1` | 产品侧：一个事务内「预警事件 → 检验记录」；设备侧：单条 `DELETE ... WHERE equipment_id=? AND batch_no=?` |
| 该批次的检验记录已定稿并进入 `ppr_history_archive` | 返回 `409` + `code=BATCH_HAS_ARCHIVED_REPORT`，**即使带 `confirm=1` 也拒绝**（归档保护只挂在产品侧，与采集数据无关） |

最后一条与第 8.1 节同源：归档表对 `ppr_eight_d_report` 是 `RESTRICT`，删到报告那步必然失败，
所以提前拦下来并给出归档号，避免用户对着英文报错猜原因。前端流程在 `src/lib/quality-delete.ts`：
**先发一次不带 `confirm=1` 的探测请求**（服务端不删任何东西）→ 拿服务端给的真实条数弹一次确认框
（`src/components/common/use-confirm-dialog.tsx` 提供的 shadcn `AlertDialog`，按钮标成「确认清理」）→
确认后才带 `confirm=1` 真删。这样用户看到的数字直接来自数据库，而不是前端估算。

删除入口只开在**批次**上（批次总览、产品台账的批次列表、设备台账的批次列表）：明细数据
（检验记录 / 采集项）只能 Excel 导入，没有新增 / 编辑 / 删除按钮；产品台账最外层（`specs`）与设备台账
最外层（`equipment`）通过 `DataManager` 的 `removable={false}` 隐藏删除按钮——规格是判定限值来源、
设备是采集数据的挂靠点，删掉会波及下游整条数据链。

## 12. 已知限制

1. **只判三个指标**。`max_wall_thickness_mm` / `max_outer_diameter_mm` / `min_outer_diameter_mm` 只存不判；规格表也没有它们的限值列。
2. **连续段按批次内时间序，不区分班次/设备**。同一批次如果有跨班次混线生产，连续 3 点可能来自不同班次。
3. **单点接近不告警**，只有连续 3 点才升级，这是需求明确要求的；零散抖动会落在正常里（事件文本会注明）。
4. **「接近」用绝对值距离，不是相对实测值的百分比**。`band` 由区间宽度决定，与实测值大小无关。
5. **判定失败静默**。`refreshAlertsQuietly()` 吞掉异常，只在服务端日志留痕，接口仍返回成功。
6. **规格缺限值时该指标静默跳过**。如果规格没配上限，判定不会报错，只是不产生事件——容易被误认为「数据正常」。
7. **全量重算的事件量随数据线性增长**，`evaluateAlerts()` 是同步的，数据量大时接口耗时会明显上升。
8. **队列可见的 `legacy` 事件被隐藏而非删除**，是为了保住历史归档的外键链，`source='legacy'` 的数据会一直留在表里。
9. **企微推送在合并窗口（默认 5 秒）后异步发出**，不在保存接口的响应里；进程在窗口内退出会丢掉待推送消息（推送状态未回写，下次重算会自动补推）。手工扫描接口会立即 flush，可以同步拿到推送结果。
10. **@ 提醒按 userid 精确匹配**，填姓名或手机号不会生效；`<@all>` 的识别依赖客户端版本，不生效时改用成员 userid 列表。
11. **推送失败不重试、不告警**，只写服务端日志 `[WecomAlert] 推送失败`。同一事件会在下一次触发重算时再次尝试（因为 `notified_level` 没写成功）。

## 14. 企业微信机器人预警推送

中/高风险事件除了进队列，还会**推送到企业微信群机器人**（`wecom-notifier.ts`）。推送是判定之后的独立环节：**推不出去不影响判定结果，也不影响业务数据写入**。

### 14.1 配置

| 配置项（`system_config`） | 环境变量兜底 | 默认 | 说明 |
|---|---|---|---|
| `wecom_alert_enabled` | `WECOM_ALERT_ENABLED` | `false` | 总开关，关闭时不产生任何外发请求 |
| `wecom_alert_webhook` | `WECOM_ALERT_WEBHOOK` | 空 | 群机器人（消息推送）Webhook 地址 |
| `wecom_alert_min_level` | `WECOM_ALERT_MIN_LEVEL` | `medium` | 最低推送级别：`medium` 中风险及以上 / `high` 仅高风险 |
| `wecom_alert_mention_list` | `WECOM_ALERT_MENTION_LIST` | 空 | 推送时 @ 的成员 **userid**（不是姓名/手机号），多个可用逗号、分号或空格分隔 |
| `wecom_alert_mention_all` | `WECOM_ALERT_MENTION_ALL` | `false` | 是否在每条预警里 @所有人，建议只在高风险场景开启 |

**Webhook 从哪来**（很容易找错地方）：群机器人自客户端 v4.1.41 起已更名为**「消息推送」**，入口一直在**群聊**里，管理后台不提供 Webhook：

- 电脑端：内部群聊 → 右上角「···」→ 消息推送 → 添加；再点对应那条 → Webhook 地址
- 手机端：内部群聊 → 右上角「···」→ 消息推送 → 添加；再点对应那条 → Webhook 地址
- 只有**创建人**能看到 Webhook；外部群不支持；群开「仅群主管理」时只有群主能加；管理员可在【管理后台 → 应用管理 → 消息推送】限制「可创建消息推送的成员」或停用该应用
- 管理后台的【应用管理 → 智能机器人 / API 模式机器人】拿到的是 **Bot ID + Secret**，那是对话机器人（回调 + `response_url` 被动回复，`response_url` 只在用户先交互时下发且一条只能用一次），**不能用来主动推告警**，不要拿它当 Webhook 用

- 优先读 `system_config`，管理员在**管理后台 → 系统设置 → 预警推送**里改，改完立即生效；环境变量只是部署级兜底。
- Webhook 含密钥，接口响应与日志一律掩码成 `key=****abcd`。
- 保存前可点「发送测试消息」直接试打（不需要先保存），测试消息同样会带上 @ 提醒，方便确认 @ 是否生效。

**@ 提醒怎么拼**：企业微信「消息推送」的 markdown / text 类型支持在 content 里用 `<@userid>` 语法 @群成员（`markdown_v2` 类型反而不支持），@所有人用 `<@all>`。消息里会多出一行：

```
> 请关注：<@all> <@zhangsan> <@lisi>
```

userid 会做清洗：剥掉 `<` `>` `@`、丢弃含非法字符或超长的项、去重、最多 20 个，避免配置写错时把标记注入进消息。**若群里 @ 没有生效**，先确认填的是 userid（企业微信「成员账号」，可在通讯录里查看）而不是姓名或手机号；`<@all>` 若不被客户端识别，改用成员 userid 列表即可。

### 14.2 只推「新异常」和「升级的异常」⚠️ 与第 7 节的重算直接相关

第 7 节说过，**导入 / 新增 / 编辑 / 删除产品数据都会重算整个批次**，重算是原地 UPDATE。所以「本次结果里有中高风险」≠「出现了新异常」：一条早就在队列里的 R5 事件，在编辑同批次另一条无关记录后仍然存在，如果只按结果推送就会重复告警；Excel 导入是逐行触发的，重复推送会很快撞上群机器人 **20 条/分钟**的限流。

因此推送条件比较的是事件的**推送状态**而非当前结果（`notified_level`，见第 6.4 节）：

```
需要推送  ⟺  risk_level ∈ {medium, high}
             且 LEVEL_WEIGHT[risk_level] > LEVEL_WEIGHT[notified_level]     // notified_level 为 NULL 时权重按 -1
```

| 场景 | 是否推送 |
|---|---|
| 事件新产生（库里原本没有） | ✅ 推送 |
| `normal → medium`（单点接近攒到连续 3 点） | ✅ 推送 |
| `medium → high`（接近升级为越限） | ✅ 推送 |
| `high → medium`（改数据后降级） | ❌ 不推（已按更高风险告警过） |
| 级别不变，只是重算 | ❌ 不推 |
| 事件回到 `normal`、或因不可判定被关闭 | ❌ 不推，**并清空 `notified_level`**，让同一记录以后再异常时重新告警 |

`notified_level` / `notified_at` **只在推送成功后回写**，所以推送失败的事件会在下一次重算时被重新识别为「未推送」并自动补推。

> **首次开启推送时**：库里 `notified_level` 还是 `NULL` 的存量中/高风险事件，会在下一次触发重算（或手工全量扫描）时被**一次性补推**。想先看格式不想打扰群里，可以先只发测试消息、确认后再开开关。

### 14.3 合并发送

判定引擎调用 `queueAlertPush()` 入队，合并窗口（`PUSH_COALESCE_MS`，默认 5 秒，从**首次入队**开始计时）到期后由 `flushAlertQueue()` 一次性发出：

- 窗口内同一事件多次入队按 `id` 去重，保留更高风险级别；
- 窗口内所有事件合并成**一条** markdown 消息，高风险在前；
- 提醒时间按 UTC 墙上时间格式化，与事件编号口径一致。

手工全量扫描（`POST /api/quality/alerts/evaluate`）会立即 flush，响应里多一个 `notify` 字段回报本次推送结果：

```json
{ "success": true, "batches": 3, "high": 3, "medium": 1, "notify": { "queued": 4, "pushed": 4, "sent": true } }
```

`notify.skipped` 的取值：`empty`（无待推送）、`disabled`（未开启或 Webhook 无效）、`below-min-level`（都低于最低推送级别）。

### 14.4 消息长这样

```markdown
# PPR 质量预警
> 识别时间：2026-11-12 10:30　高风险 1 条　中风险 1 条
> 请关注：<@all> <@zhangsan>
## 高风险（1）
**QE-20261112-003WT**　壁厚　超出标准区间
> 批次 12121D0053　PPR S2.5 25×4.2 瓷芯管　2026-11-19 09:20
> 4.200 mm–4.800 mm，实测 4.180 mm，低于下限 0.020 mm
> 检验记录 IR-20261112-003
## 中风险（1）
**QE-20261111-004WT**　壁厚　连续3点接近区间边界
> 批次 12121D0051　PPR S2.5 25×4.2 瓷芯管　2026-11-17 15:40
> 4.200 mm–4.800 mm，连续 3 点进入接近带（距下限 ≤ 0.090 mm，为区间宽度的 15%）：4.285 / 4.270 / 4.255
> 检验记录 IR-20261111-004
```

每个级别最多展开 `MAX_ITEMS_PER_LEVEL`（默认 8）条，其余折叠成一行；内容按 UTF-8 字节数截断，避免超出 markdown 4096 字节上限被机器人拒收。

### 14.5 调用链与失败处理

```
evaluateAlerts()  ──事务提交后──▶  queueAlertPush()  ──合并窗口到期──▶  flushAlertQueue()
      │                                    │                                    │
   判定+写库                        只入队、不发请求                    读配置 → 组装 markdown → POST 机器人
                                                                              │
                                                                      成功才回写 notified_level
```

- **入队失败**：`console.error('[AlertEngine] 企微推送入队失败')`，判定结果照常返回。
- **发送失败**（HTTP 非 2xx、`errcode ≠ 0`、超时 8 秒）：`console.error('[WecomAlert] 推送失败')`，不写推送状态，下次重算补推。
- 推送是异步的，**import/编辑接口的响应里看不到推送结果**，只有手工扫描接口会 flush 并回报。

### 14.6 验证步骤

1. 管理后台 → 系统设置 → 预警推送：填 Webhook → 「发送测试消息」，群里收到即配置可用（若要 @人，同时填好 userid 名单或打开 @所有人，测试消息里就能看到 @ 效果）。
2. 打开「推送中/高风险预警」开关，最低级别选「中风险及以上」。
3. 到数据管理（批次总览页）导入 `PPR/测试数据/演示告警数据/产品数据/` 里的 `12121D0051`（壁厚连续 3 点接近）与 `12121D0053`（三处越限），5 秒内应收到一条合并消息。
4. **去重验证**：导入完成后手工点两次「全量扫描」，健康的重算**不应**再收到告警（事件级别没变，`notified_level` 已写）。注意：把同一个 Excel **再导入一遍**不会产生新事件——检验记录按 `record_no` 覆盖写入（幂等），事件级别没变就不再推送。
5. 把 Excel 里某条越限值改回区间内、重导一次，再改回越限、再重导：应重新收到一次高风险推送（事件回到正常时推送状态被清空）。
